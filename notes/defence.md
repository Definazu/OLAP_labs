# Репетиция защиты

## Что сказать простыми словами

> Я сделал витрину оборота розничной сети за первый квартал 2024 года. Одна строка факта — одна товарная позиция продажи. Например, десять упаковок молока на 25 денежных единиц — это одна позиция. Я проверяю исходные CSV на пропуски, дубли и неверные ссылки, а затем загружаю данные в DuckDB и ClickHouse. У товара может меняться категория. Я храню обе версии и выбираю нужную на дату продажи. Сумма позиций по запросу `canonical_metric.sql` равна 264,00. Карточка Metabase показывает ту же сумму. При выборе Запада оба расчёта дают 153,50.

| Вопрос преподавателя | Ответ, который можно произнести |
|---|---|
| Что означает строка `fact_sales`? | Одна товарная позиция с ключом `sale_id`. Например, 10 упаковок молока на 25,00 — одна строка. Число строк показывает, сколько было позиций. Число чеков из этих данных восстановить нельзя. |
| Где эталон оборота? | В `sql/canonical_metric.sql`. Он складывает `amount` по всем позициям с 1 января по 31 марта 2024 года. Деньги хранятся как `DECIMAL`, чтобы сравнивать суммы до сотых. |
| Зачем ставить `date_id` первым в `ORDER BY`? | Большинство вопросов начинается с периода. Когда данные отсортированы сначала по дате, ClickHouse может пропускать блоки за пределами диапазона. По условию на январь в примере остаётся одна часть из трёх. При фильтре только по магазину остаются все три. |
| Чем отличается месячная партиция от `ORDER BY`? | Партиция делит данные по месяцам. `ORDER BY` задаёт порядок строк внутри частей и помогает пропускать диапазоны. Проверку уникальности `sale_id` выполняет ELT. |
| Зачем SCD2? | С 1 февраля для товара 101 действует категория «Молочные напитки». Продажа 14 февраля на 22,50 попадает в неё. Две январские продажи на 45,00 остаются в категории «Молочка». |
| Зачем отдельный агрегат? | Для графика оборота по месяцам заранее считаю суммы по дням и магазинам. График складывает их до месяца. Если нужно проверить точность итоговой карточки, эталон считается по детальным позициям. |
| Что произойдёт при повторной загрузке или ошибке? | Успешный повтор публикует свежий снимок с теми же 15 позициями и суммой 264,00. Если в CSV указан магазин, которого нет в справочнике, загрузка останавливается до публикации. |
| Какие ограничения стоит назвать? | CSV не содержит возвратов и номеров чеков. Если в справочнике магазина поменять регион, старые продажи этого магазина будут отнесены к новому региону. История хранится для категории товара. |

## Что показать по порядку

Откройте [паспорт](../passport.md), [лог проверок](../evidence/p04-p09-verification.log) и дашборд. В терминале выполните `docker compose exec -T clickhouse clickhouse-client < sql/canonical_metric.sql`. На дашборде сначала оставьте регион пустым, затем выберите «Запад». Для второго числа выполните `docker compose exec -T clickhouse clickhouse-client < sql/reconcile_regions.sql` и найдите строку «Запад».

| Время | Что показать |

| 0:00–1:15 | Паспорт, зерно, три измерения, источник денежной меры. |

| 3:45–4:45 | `ORDER BY`, месяц партиции, `EXPLAIN` для дат и магазина. |
| 4:45–6:00 | Эталонный SQL, дашборд и смену региона на «Запад». |

## Вопросы для самопроверки и репетиции в паре

1. Что означает одна строка `fact_sales`? Почему по `COUNT(*)` нельзя посчитать средний чек?
2. Где зафиксирован эталон, каков период и почему у денег тип `DECIMAL`?
3. Как дата продажи определяет `product_sk`? В какой категории продажа 14 февраля по товару 101?
4. Что отсечёт месячная партиция при запросе за январь и почему один `store_id` помогает меньше?
5. Что совпадает в SQL и BI при выборе региона «Запад»? Что произойдёт со старым отчётом после смены региона магазина?

## Короткие ответы по теории

| Билет | О чём сказать |
|---|---|
| 1 | OLTP обслуживает операции, OLAP агрегирует согласованные исторические факты. Источник → ELT → витрина → SQL → BI. |
| 2 | Зерно — смысл строки. `amount` аддитивна. `COUNT(*)` считает позиции, а чекового ключа в исходнике нет. |
| 3 | Star присоединяет денормализованные измерения к факту. Snowflake разбивает их на справочники. Constellation связывает несколько фактов через согласованные измерения. |
| 4 | SCD1 меняет атрибут во всех срезах. SCD2 хранит версии. Дата события выбирает интервал `[valid_from, valid_to)`. |
| 5 | Slice ограничивает один разрез, dice несколько. Roll-up поднимает уровень агрегации. Эталон фиксирует формулу и период. |
| 6 | DuckDB работает в процессе, читает CSV и Parquet. ClickHouse обслуживает BI как отдельный сервер. |
| 7 | ELT загружает сырьё в staging, проверяет и преобразует в базе. Идемпотентный повтор сохраняет число строк и оборот. |
| 8 | `ORDER BY` определяет физический порядок и помогает разреженному индексу. Уникальность `sale_id` проверяет ELT. |
| 9 | Партиция задаёт куски хранения. Агрегат заранее считает суммы под график. Канон остаётся на детальном факте. |
| 10 | Metabase читает ClickHouse. При одинаковом определении, периоде и регионе карточка и SQL дают один итог. |
| 11 | Kimball использует согласованные измерения и витрины. Inmon начинает с корпоративного хранилища. Data Vault хранит ключи в hubs, связи в links, историю атрибутов в satellites. Паспорт, DDL и проверки описывают витрину курса. |
| 12 | Классификация, регрессия, кластеризация, поиск ассоциаций. Признаки берутся из витрины на подходящем зерне, с учётом времени события и риска утечки. |
